# Known issues (executable registry)

Single source of truth for defects we **know about and have not fixed yet**. Each one has
a test that states the *correct* behaviour and is currently expected to fail, so the
suite stays green but the bug can never be forgotten or silently "fixed" without the
registry being updated.

## How the tests work

| Side | Where | Mechanism |
|---|---|---|
| Backend | `backend/tests/known_issues/` | `@known_issue("KI-xxx", ...)` = `xfail(strict=True, raises=AssertionError)` |
| Frontend | `frontend/lib/knowledge/known-issues.test.tsx` (currently none open; the file is recreated when one is added) | a "today" test pinning current behaviour + an `it.fails` test of the correct behaviour |

*Strict* means: when a fix makes the test pass, the suite goes **red** (XPASS / `it.fails`
passing). The fixer then removes the marker (backend) or changes `it.fails` to `it`
(frontend), and moves the entry below from **Open** to **Fixed**. Run them with:

```bash
cd backend  && uv run pytest tests/known_issues -rxX      # expect "passed, N xfailed"
cd frontend && npx vitest run lib/knowledge/known-issues.test.tsx   # only while a frontend issue is open
```

The KI-022, KI-031, KI-032 and KI-033 tests need the disposable PostgreSQL (`SESSION_TEST_DATABASE_URL`, see `backend/app/security/README.md`) and are reported as skipped without it; everything else in that folder runs without containers.

Rule for new entries: reproduce first, assert only what a user would call correct, add a
passing "guard" test for any neighbouring behaviour a fix must not break, and never mark
something known without a test (or say plainly that it is *unreproduced*).

### KI-022 — Wordy search queries find nothing (recall cliff)  *(retrieval quality, backend, reproduced by the evaluation; the keyword part has a strict test, the agent's own query writing stays a RAG evaluation case)*
- **Test (M0 ticket 02, 2026-11-21):** `tests/known_issues/test_ki022_keyword_all_words.py`. Against a real PostgreSQL (it skips without `SESSION_TEST_DATABASE_URL`), keyword retrieval returns **0 hits** for both the user's question and the agent's rewrite although the handbook sentence is indexed, while `annual leave days per year` finds it (that one is a passing guard). No paid call is involved.
- **Progress (2026-11-20, Step 1b):** generic and tiny file-name words no longer boost files (a question word must be 5+ letters and in at most 2 file names), and one long document can no longer fill all 8 slots (limit 3 per file). `sf07` and `mx07` now find their file. Still open: the all-words keyword search and the agent's own query writing (Step 1c).
- **Progress (2026-11-20, Step 1a):** the vector cut-off part is fixed: default `RETRIEVAL_SCORE_THRESHOLD` 0.35 -> 0.25, plus a new `RETRIEVAL_RELATIVE_THRESHOLD` 0.7. `sf01` now passes (dev, agent level), and the retrieval probe finds the right file for 98 % of plain questions (was 93 %). Still open: the all-words keyword search (Step 1b/1c) and generic file-name words that flood results (Step 1b). See `docs/EVALUATION_RESULTS.md`.
- **Symptom:** "How many days of annual leave do employees get per year?" answers "I could not find relevant information" (3 of 3 tries, tool agent) although the handbook says "Annual leave is 22 working days per calendar year."
- **Cause (measured):** the agent searches with the model's rewrite, `annual leave entitlement days per year employees get`. Vector retrieval returns 0 (all hits are below `retrieval_score_threshold = 0.35`) and keyword retrieval returns 0 (`websearch_to_tsquery` requires every word; "entitlement" and "get" are not in the file). `annual leave days per year` finds the file (keyword hit plus a 0.37 vector hit).
- **Reproduce:** the keyword part: `cd backend && uv run pytest tests/known_issues/test_ki022_keyword_all_words.py -rxX` (needs the disposable PostgreSQL). The end-to-end symptom: `cd backend && uv run python -m evaluation.rag_eval.cli setup` then run the question through `RagService` on the `drivemind_eval_v2` store (see `docs/EVALUATION_RESULTS.md`). That needs an OpenAI key, because the wording of the agent's rewrite comes from the model, so it stays an evaluation case.
- **Not fixed on purpose:** changing the threshold or the keyword mode changes retrieval for everything and needs its own evaluation. The corpus here has many whole-file chunks, which probably makes the effect stronger than on long documents (unmeasured).
- **Suggested direction:** make keyword matching tolerant (any-term ranking instead of all-terms), and compare a lower or relative vector threshold on the same cases before and after.

### KI-031 — Six services pick an arbitrary owner's Google credential when no owner is given  *(security, latent, backend, found by M0 ticket 03; not reachable today)*
- **Test (M0 ticket 03, 2026-11-21):** `tests/known_issues/test_ki031_credential_owner_fallback.py` (needs the disposable PostgreSQL; skipped without `SESSION_TEST_DATABASE_URL`). With two owners who each hold an ACTIVE credential, `_resolve_user(None)` in the drive-sync, drive-content, chunking, ingestion and indexing services, and `resolve_active_user(db, settings)`, each return a real owner instead of refusing: 6 strict expected failures. 12 passing guards show that an explicit owner still resolves to exactly that owner. The assertion does not depend on which owner PostgreSQL returns first, so it is deterministic. `tests/security/test_owner_fallback_callers.py` (no database) is the protective side: every production caller passes an explicit owner, and no seventh unscoped credential select exists.
- **Cause:** `select(GoogleOAuthToken).limit(1)` with no owner filter and no ordering, then `db.get(User, token_row.user_id)`, in `services/user_resolution.py:54`, `drive_sync_service.py:70`, `drive_content_service.py:53`, `chunking_service.py:57`, `ingestion_service.py:77`, `indexing_service.py:71`. It runs when `user_id is None`, which the `UUID | None` signatures allow. With one owner this is "the" owner; with two it is whichever row PostgreSQL returns first.
- **Why it is latent, not reachable:** every mounted route gets its owner from `require_resource_user` / `require_index_user` (a session principal's `corpus_user_id`, or the demo user in demo mode); the indexing worker passes `claim.user_id`; the demo loader and the evaluation harness pass explicit ids; the RAG path rejects a non-UUID owner. Full caller table: `docs/tickets/m0-system-audit/03-credential-fallbacks-and-ownership.md`.
- **Pinned by an existing test:** `tests/services/test_user_resolution.py::test_normal_mode_preserves_first_oauth_token_resolution` asserts the fallback (including the `LIMIT 1`). The fix must replace it, and about 60 service unit tests that call the owner-less path (`ingest_files()`, `build_index()`, `chunk_documents()` and similar) must pass an owner.
- **Not fixed on purpose:** M0 only audits. The fix is the proposed M0-SEC (see the ticket): make the owner mandatory in the six places, then delete the dead owner-less entry points.
- **Direction:** `user_id: uuid.UUID` (required), raise `ValueError("An explicit corpus owner is required")` as `RagService._resolve_user` already does; remove `select(GoogleOAuthToken).limit(1)`; shrink the allow-lists in `test_owner_fallback_callers.py`; remove the marker from the six tests.

### KI-032 — An abandoned Google login attempt is never removed by the running application  *(security hygiene / availability, backend, found by M0 ticket 04; reachable only while `GOOGLE_APPLICATION_SESSIONS_ENABLED` is on, hosted value unverified)*
- **Test (M0 ticket 04, 2026-11-21):** `tests/known_issues/test_ki032_pending_login_state_growth.py` (needs the disposable PostgreSQL; skipped without `SESSION_TEST_DATABASE_URL`). Three login attempts are started and never finished, their ten minutes pass, then a fourth login starts: the three expired rows are still in `oauth_pending_states` (1 strict expected failure). One passing guard: starting a login does not remove another browser's still-valid attempt, so a fix must not do that. The test was also run against a temporary one-line prune in `start()` and passed, so it is satisfiable.
- **Cause:** `POST /api/v1/auth/session/google` with intent `LOGIN` needs no session, only a matching `Origin` header and `X-DriveMind-Auth: 1` (plain request headers, so any HTTP client can send them). Each call commits one `OAuthPendingState` row. A row is deleted only when its callback consumes it (`google_session_auth_service.py` `_consume`). The only sweep of expired rows is `GoogleOAuthService._cleanup_expired_pending_states`, called from the legacy `handle_callback`, which belongs to the unmounted router `app/api/auth.py`. No rate limit exists for this endpoint (see ticket 04, "Abuse protection").
- **Impact:** one small row per request, growing without limit. A row holds a PKCE verifier, a nonce and hashes; it cannot be redeemed after it expires, so this is storage growth, not an authentication or data-isolation weakness.
- **Not fixed on purpose:** M0 only audits.
- **Direction:** delete expired rows when a login starts (the legacy callback did it at callback time), or sweep on a schedule; plus a request limit on this endpoint (Owner decision, ticket 04). If the fix is a scheduled sweeper, rewrite the test to call it instead of `start()`.

### KI-033 — An owner who has submitted a question cannot be deleted from `users`  *(data lifecycle, backend, found by M0 ticket 07; not reachable today, blocks a future Delete stored data)*
- **Test (M0 ticket 07, 2026-11-21):** `tests/known_issues/test_ki033_user_delete_blocked_by_turns.py` (needs the disposable PostgreSQL; skipped without `SESSION_TEST_DATABASE_URL`). `DELETE FROM users` for an owner with one conversation turn, answered or unanswered, is refused with a foreign-key violation and rolled back: 2 strict expected failures. The passing guard (`tests/security/test_conversation_deletion_privacy.py::test_deleting_a_user_who_never_asked_a_question_cascades_to_every_owner_table`) shows the cascade empties all ten per-owner tables for an owner with no turn, and leaves another owner untouched.
- **Cause:** `conversation_turns` has two foreign keys with no `ON DELETE` rule: `fk_turns_session_owner` (to `application_sessions`) and `fk_turns_result_owner` (to `query_history`). The cascade from `users` reaches those two tables while a turn still points at them, so PostgreSQL refuses (`alembic/versions/20261015_1200_conversations.py`, `db/models/conversation_turn.py`).
- **Why it is not reachable:** no application code deletes a `users` row (ticket 07 route and code search).
- **Not fixed on purpose:** M0 only audits; a fix is a migration and belongs with Delete stored data (M7).
- **Direction:** give both foreign keys `ON DELETE CASCADE` (or delete turns first) in a migration, then remove the marker from the two tests.

## Fixed
### KI-026 — A reply that cited a source marker that did not exist ended in an error instead of an answer  *(fixed on branch `fix/ki026-citation-retry`, 2026-11-20)*
- **Was:** the model sometimes wrote a marker that does not exist (`[source_2]` when only `source_1` exists). `finalize_answer` rejects that on purpose (an invented marker is never repaired by deleting it or adding real ones), so the run ended as `UNSAFE_FINAL_OUTPUT` and the user saw `ChatError`. 3 of 14 traced runs of "What is the late payment fee on invoice INV-0457?"; 3 errors in 146 end-to-end questions.
- **Fix (`graph.py`, `finalization.py`, `agent_state.py`):** only for a marker that does not exist (`UnknownCitation`), the model gets **one** corrective turn: a server note names the valid source handles (never bare numbers, never handles the model was not given) and the rewrite is checked by exactly the same rules. A leaked handle or id, a second bad marker, or a run with no model call left (cycle limit) still fails at once. While streaming, a `validating` state event clears the rejected prose on the client before the corrected answer streams. Tests: `tests/agents/tool_rag/test_citation_retry.py` (8; with the retry disabled 3 of the first 6 fail), `tests/test_chat_streaming.py`, `test_grounding_policy.py`.
- **Evidence (`gpt-5.4-nano`):** the late-fee question, 40 counted real runs (two batches of 20; the second after the review changes): the bad marker appeared in 2 runs, the retry corrected both, **0 errors**; before: 3 of 14. A first batch of 20 saw the bad marker in 4 runs; its error count was not recorded, so it is not used. Messy set 34 -> **36 of 39**, errors 2 -> 0 (`vi05`, `vi08` now answer). Full backend suite: 2924 passed, 3 skipped.
- **Known cost:** a retry means one more model call, and the claim check runs again on the rewrite (a second small call). It happens in about 1 run in 10 on that question and rarely elsewhere.
- **Limit:** if the model repeats a bad marker, the user still gets the error; the retry is deliberately limited to one.

### KI-025 — A question with an identifier like "INV-0457" was answered with "No eligible indexed file matches that name"  *(fixed on branch `fix/ki025-recovery`, 2026-11-20)*
- **Was:** the model sometimes passed the identifier to `resolve_file`, which matches exact file names only, so the lookup always failed, and a failed lookup blocked the answer for the whole run. Messy set: 3 of 7 invoice questions got no answer; first-step probe 25 of 70 first calls went to `resolve_file`.
- **Fix (`app/agents/tool_rag/`):** (1) `finalization.provenance_response`: a NOT_FOUND for a reference that does not end in a file extension ("soft") is cleared by a later successful content read in the same run; one that does look like a file name (`budget_2027.txt`) stays final, so a missing file is never answered from other documents. (2) `file_reference.names_a_file` is the one structural rule both parts use. (3) The NOT_FOUND result carries a hint the model sees: file names match exactly and numbers or topics are searched, or for a file-shaped name, tell the user and do not answer from other files. (4) The `reference` argument wording from the earlier partial fix is kept. Tests: `tests/agents/tool_rag/test_name_lookup_recovery.py` (18, a mutation check showed 2 of them fail without the fix), `test_tool_contracts.py`.
- **Evidence:** a held-out set written before the work (`rag_v2_identifier_cases.json`, 19 questions): the question that always went to the wrong tool (`id14`) now answers correctly in 10 of 10 runs (lookup -> hint -> search -> "$350.00" with citation); set 14 -> 16 of 19 (the other gain, `id04`, is a retrieval question that flips between runs, KI-027). Older dev set 77 -> 78 of 88; test-split first tool identical case by case; `ru06` and `pb02` 20 of 20 searched; messy set 35 -> 34 of 39 (two `ChatError` replies, KI-026; `vi06` replaced by `vi08`, see `docs/EVALUATION_RESULTS.md`).
- **Tried and rejected:** advice in the tool description or the system prompt moved the target question but changed unrelated ones (`ru06`, `pb02`, older dev set 77 -> 72); see `docs/DECISIONS.md`.
- **Limit:** prevention is not fixed (the model still picks the lookup first for some phrasings, `id14` 10 of 10); the fix makes that harmless. If a model does not search after the hint, the user still gets the "No eligible indexed file" text.
- **Evaluation changes made with it:** `judge_row` fails a "not found" reply that is the file-lookup failure text (wrong route) unless the case names a file (`names_a_file`); `vi06` replaced by `vi08`; `first_step_probe --dataset/--with-messy`; `cli rescore` reads the datasets from the result file.

### KI-024 (XLSX part) — Excel files and Google Sheets were not read at all  *(fixed on branch `feat/extraction-a5-xlsx`, Stage A5)*

Spreadsheets were not a supported type, so they were never indexed. Each visible sheet is now a Markdown table under `## Sheet: name` (first non-empty row as header, calculated values, ISO dates). Size is capped and every cut is announced in the text with a `Note:` line, so the assistant can say it saw only part of a sheet: 1,000 rows and 50 columns per sheet, 5,000 rows and 25 sheets per workbook, 500 characters per cell, files over 30 MB refused. Google Sheets are exported as XLSX (CSV, first sheet only, when Drive says the export is too large). `.csv` files (Markdown table) and `.md` files (as text) are supported too. Hidden sheets, charts, pivot tables, number formats and formulas without a stored result are not read. Tests: `tests/ingestion/test_xlsx_extractor.py`, `test_csv_and_tabular.py` (15 of 16 deliberate breakages caught; the 16th is equivalent on this Python), `tests/connectors/test_google_drive_client.py`, frontend `single-file-preparation.test.tsx`, and the former known-issue test in `tests/known_issues/test_ki024_file_readers.py`. Spreadsheets already in Drive are found by one full scan.

### KI-002 — A real citation did not prove the claim  *(fixed on branch `fix/claim-grounding`)*
- **Was:** a claim the source does not say, carrying a valid `[source_N]` marker, was shown with a genuine citation (evidence "Authoritative refund policy text."; answer "Refunds are always approved within 90 days. [source_1]" was published).
- **Fix:** after the tool agent answers, `claim_check.py` asks `CLAIM_CHECK_MODEL` (default `gpt-5.4-mini`) which numbered statements assert a specific fact the evidence lacks or contradicts and removes them before citation handling; if nothing supported is left the normal "could not find" reply is used. It fails open (errors leave the answer unchanged), skips headings and fragments, and can be turned off with `CLAIM_CHECK_ENABLED=false`. One extra call per grounded answer: about +1.4 s median latency.
- **Measured (docs/EVALUATION_RESULTS.md, corrected test, two runs):** removes an invented sentence 41/41, catches a changed number 25/26, wrongly removes 0/41 true answers and 1/8 correct calculated answers; on RAGBench (general data, GPT-4o labels) precision 0.52 / recall 0.46 at response level. Not perfect: a wrong claim that is only implied by the evidence passes, a number changed inside a long sentence can slip through (`sv04`), and a unit conversion (minutes to hours) can be removed.
- **Scope:** tool agent only. The legacy pipeline and the LangGraph path are not checked.
- **Tests:** `backend/tests/agents/tool_rag/test_claim_check.py` (55); the former xfail test was removed.

### KI-010 — A finished preparation record blocked Drive discovery  *(fixed on branch `fix/discovery-preparation-gate`)*
- **Was:** after documents finished preparing, "Check Drive" refused until the Preparation screen was closed.
- **Fix:** `DiscoveryController` now asks the canonical `readPreparationGate`. A queue whose every document is confirmed ready is *cleared* (same as "Close completed preparation") and discovery proceeds. Pending, failed, skipped, legacy, unreadable, wrong-owner or unknown-version records still block and are never modified.
- **Why cleared, not merely ignored:** a later sync can change a prepared file, after which the completed record could no longer be verified, and "Close completed preparation" is disabled for unverifiable batches. Leaving the record would trap the user.
- **Tests:** `lib/knowledge/discovery-preparation-gate.test.tsx` (22) and one UI test in `components/files/drive-discovery.test.tsx`.

### KI-011 — The refusal named the wrong cause  *(fixed on branch `fix/discovery-preparation-gate`)*
- **Was:** every local refusal said "The Drive check was not accepted. Verify your connection…" though the backend was never called.
- **Fix:** typed `DiscoveryBlockedError` reasons with their own messages (unfinished preparation, unreadable preparation record, a discovery already pending in this browser, no safe tab coordination). ### KI-012 — "Check status" could do nothing  *(fixed on branch `fix/check-status-join`)*
- **Was:** `PreparationQueue.check()` and `DiscoveryController.check()` did `if (busy) return`, so a click during any running check, or during a submit/confirm, was discarded instantly. The screens also poll every 3 to 5 seconds, so the button often landed mid-poll. And a check that found the same blocked message republished it unchanged, so even a real check looked like nothing happened.
- **Fix (control):** `lib/knowledge/joined-check.ts`. A click during a status check *joins* it (shares its single network read and resolves only when it truly finishes); a click during another operation waits for that operation, then checks. A finished check is never replayed from cache. Clicks can never submit work.
- **Fix (feedback):** `useManualCheck` shows "Checking…" (button disabled), then "Checked at HH:MM:SS. No change." or "Status updated." on the discovery buttons and the Preparation screen, so the outcome is always visible.
- **Deliberately not changed:** the "Check for files" (start) action still ignores a click while a check is running. Making it wait could let two submissions race, so it needs its own design.
- **Tests:** `joined-check.test.ts` (6), `check-status-join.test.tsx` (8, 4 fail without the fix), plus UI tests in `drive-discovery.test.tsx`, `preparation-progress.test.tsx` and `queue-preparation.integration.test.tsx`.

### KI-020 — Indexing admission was a permanent fail-closed latch  *(fixed on branch `fix/indexing-recovery`)*
- **Was:** any error in the indexing supervisor (even one slow database check on a busy machine) set `FAILED` for good; only a process restart reopened admission. Seen once locally as a flaky test (about 1 in 3 full runs under load) and once on the hosted app after a transient provider problem.
- **Fix:** the supervisor now separates a *momentary outage* from *real damage* (`is_transient` in `indexing_runtime.py`). Timeouts, dropped or refused connections and brief Qdrant or database unavailability are retried with backoff inside a bounded window (`INDEXING_OUTAGE_TOLERANCE_SECONDS`, default 30). One success resets the window. When the window runs out it closes exactly as before. A missing table or column, constraint errors, configuration or identity mismatches, vector-collection changes, any unknown exception, a failure while *executing* a stage, and incomplete session cleanup still close immediately. The unclear case stays fail-closed.
- **Also:** one admission probe that fails momentarily now refuses that one request (503) instead of closing the door for everyone; `check_database` no longer reports a broken schema as "unavailable"; a dead task always leaves a fixed diagnostic code (`EXECUTOR_TASK_FAILED`); `/api/v1/health/indexing` shows a fixed `degraded` code while a dependency is retrying. No error text is ever logged or exposed.
- **Tests:** `backend/tests/security/test_indexing_outage_recovery.py` (38) and one in `test_normal_indexing_runtime.py`. The existing fail-closed tests were kept; only the idle-claim-stall test got a tiny window so it still proves the bound.
- **Observed after the fix (2026-11-19):** in one full run on a machine busy with other work, two lifecycle tests (`test_normal_lifespan_synthetic_two_owner_pipeline_and_exact_job_polling`, `test_normal_issued_build_with_lost_acknowledgement_remains_blocked`) got a 503 on their first admission. Both pass alone, under CPU load, and in a later quiet run of all of `tests/security` (1026 passed). The cause was not reproduced; the likely cause is the new one-request refusal on a momentary probe error. That refusal is now logged with a fixed code so a recurrence names its cause. Watch for it.

### KI-021 — A PDF whose text contains a NUL character could not be stored  *(fixed on branch `fix/pdf-nul-characters`)*
- **Found by:** loading the evaluation corpus. 3 of 22 real research papers (math-heavy, large brackets) extract with U+0000, and PostgreSQL rejects it (`invalid byte sequence for encoding "UTF8": 0x00`). The ingestion code only catches extraction and Drive errors, so the database error was not handled per file.
- **Fix:** `normalize_extracted_text` (shared by every extractor) now drops U+0000 and changes nothing else.
- **Tests:** `test_pdf_extractor.py::test_extract_pdf_text_drops_nul_from_math_fonts` and two in `test_plain_text_extractor.py` (all three fail without the fix).
- **Not changed:** a persist-time database error on one file still is not turned into a per-file `FAILED`. That is a separate, wider question; this fix removes the one cause seen.
